# Feature overlap matrix — Mealie vs. Grocy

PLAN.md requires, for every overlapping capability between the two reference systems, one of
`MEALIE` / `GROCY` / `MERGE` / `REDESIGN` / `DEFER` / `OMIT`, with a stated reason — explicitly
never "take the best parts." This document is that decision, built from the completed
investigations: `mealie-recipe-model.md`, `mealie-planning-and-search.md`,
`mealie-api-and-database.md`, `grocy-inventory-and-stock.md`, `grocy-units-and-planning.md`,
`grocy-api-and-database.md` (all in this directory).

Each row also names the OpenSpec change the decision is now recorded in, so this matrix is a
navigation aid, not a second source of truth — the design reasoning lives in the change itself.

| Capability | Decision | Why | Recorded in |
|---|---|---|---|
| **Recipe content model** (structured ingredients, foods, units-per-line, tags, categories, images) | **MEALIE**, as a starting shape only | Mealie is recipe-first with a real structured-ingredient model; Grocy's recipe feature is secondary and stock-consumption-focused, with a far thinner content model. But Mealie's own `RecipeIngredientFood`/`Unit` distinction is looser than the Ingredient-vs-Product split this project requires — copy the shape (ingredient lines with food+unit+quantity), not the exact schema. | `implement-recipe-family-and-revisions`, `establish-household-and-catalog` |
| **Recipe revision/version history** | **REDESIGN** — no prior art from either system | Mealie has zero revision history in its 62-table schema; edits overwrite in place (confirmed, and a live-reproduced `PATCH` bug corrupted a recipe with no recovery path). Grocy doesn't model recipe versions at all. Neither system offers anything to merge or copy here — `RecipeFamily`/`RecipeVariant`/`RecipeRevision` is designed fresh from `PLAN.md`'s reasoning alone. | `implement-recipe-family-and-revisions` |
| **Ingredient vs. Product distinction** | **MERGE**, informing an already-decided split | Mealie's "Food" is closer to a canonical ingredient (no packaging/brand) but doesn't cleanly separate fresh/dried/canned forms. Grocy's "Product" is an inventory-item concept (closer to purchasable `Product`) with zero relation to any canonical-ingredient concept — Grocy products ARE the base unit, full stop. Spisordning's already-decided two-tier `Ingredient`/`Product` model sits between the two and is validated by neither system cleanly solving it alone. | `establish-household-and-catalog` |
| **Units & unit conversion** | **REDESIGN** — no safe prior art | Mealie has no unit conversion system at all. Grocy has one, but it has a confirmed, live-reproduced bug (a trigger silently auto-inserts a wrong 1:1 conversion when purchase/stock units differ, which then collides with an explicit factor). Neither is safe to copy; build fresh with an explicit regression test targeting Grocy's exact failure mode. | `establish-household-and-catalog` (invariant 11), `implement-pantry-inventory` (task 9.6) |
| **Meal planning (weekly plan → recipe link)** | **MEALIE**, informing scope | Mealie has a real, mature weekly meal-planning UI directly linking plan slots to recipes. Grocy's "meal plan" exists mainly to drive stock consumption forecasting, not household planning UX. Spisordning's existing `meal_plan`/`meal_plan_candidate`/`meal_plan_decision` schema and scorer already exceed both in one respect neither has: explainable, deterministic ranking with a stored score breakdown. | `implement-meal-planning` |
| **Shopping lists** | **MERGE** | Mealie's shopping-list UX (household-facing, editable, mergeable across plans) is the better model for the human-editable list this project's `shopping_requirement → shopping_list` pipeline needs. Grocy's shopping list is tied to stock-below-minimum triggers — a genuinely useful signal Mealie lacks, worth carrying forward as a future recommendation/shopping-suggestion input, not as the list's core model. | `implement-shopping-and-commerce` |
| **Households / users / person identity** | **REDESIGN**, informed by a confirmed Mealie gap | Mealie conflates login credential and food-domain person in its `users` table — confirmed live: it cannot model a child household member without giving them a login account. Grocy is effectively single-tenant-oriented with weak multi-household modeling. Spisordning's already-decided `Account`/`Person`/`HouseholdMembership` split (an explicit non-goal to conflate, per `PLAN.md`) is validated as solving a real limitation, not a hypothetical one. | `establish-household-and-catalog` (invariant 1) |
| **Ratings / favorites** | **REDESIGN**, informed by a confirmed Mealie incident | Mealie's own migration history documents a real, permanent data-fabrication incident: an original group-wide rating column was retrofitted to per-user scoping with the migration comment "since we don't know who rated the recipe initially, we copy the rating to all users." Spisordning's person/meal-instance-scoped `MealReview`, decided independently of Grocy or Mealie, is exactly the design that incident would have prevented. | `implement-meals-and-preferences` |
| **Inventory / stock / pantry ledger** | **GROCY**, with two explicit divergences | Grocy is the only reference system with a real, years-battle-tested inventory ledger — its `stock`/`stock_log` split is the closest prior art to this project's ledger-plus-projection design, and directly validates it: Grocy's `stock` table alone provably loses history (rows are deleted at zero quantity). Two deliberate divergences: (1) Grocy's "undo" mutates a historical `stock_log` row in place — Spisordning requires undo to be a new, compensating event, never a rewrite of history; (2) Grocy's `stock` table's row-deletion-at-zero is explicitly not copied — Spisordning's lot rows persist (closed, not deleted) so the ledger and the projection never diverge in what they can answer. | `implement-pantry-inventory` (D2, D7) |
| **Inventory event vocabulary** (PURCHASE/CONSUME/DISCARD/ADJUST/TRANSFER/MARK_EMPTY/OPEN) | **REDESIGN** (six kinds, not seven) | Grocy has no distinct `MARK_EMPTY` transaction — it's UI sugar over `CONSUME` with the full remaining quantity, confirmed by source inspection. `MARK_EMPTY` collapses into a `CONSUME` event with `source: 'mark_empty'`, kept as a convenience *command*, not a persisted *kind*. `DISCARD` stays distinct — Grocy modeling discard as `CONSUME`-with-a-`spoiled`-boolean is a confirmed weakness (spoilage deserves first-class, queryable status), not a pattern worth copying. | `implement-pantry-inventory` (D7) |
| **Inventory confidence / uncertainty** | **DEFER to `PLAN.md` reasoning alone** — genuinely no prior art | Grocy has zero uncertainty modeling of any kind; every quantity is treated as exactly known. This is the one pantry-inventory decision (confidence stored on the lot, justified per-event) that Grocy's real-world evidence neither supports nor contradicts — recorded explicitly so this isn't mistaken for a validated decision later. | `implement-pantry-inventory` (D3) |
| **Barcode / GTIN lookup** | **DEFER** | Neither investigation went deep on external barcode-database integration (Open Food Facts) within the reference systems themselves — this remains a `implement-pantry-inventory` research/implementation task on its own footing, not something either reference system settles. | `implement-pantry-inventory` (section 7) |
| **Recipe availability / cost-against-stock** | **GROCY informs domain scope; REDESIGN the implementation** | Grocy is the only system that even attempts "can I make this recipe from what I have" — but its implementation is ~100-line nested SQL views producing an opaque `possible_servings` number with no per-ingredient breakdown surfaced anywhere. The domain question is validated as real and worth solving; the "black box aggregate with no explanation" implementation shape is the clearest anti-pattern found across both systems and is explicitly not copied. | `implement-recipe-availability` |
| **Cookbooks / recipe collections** | **REDESIGN** | Mealie's "cookbook" is a saved search filter with no recipe-membership table — it cannot represent "this recipe was reviewed and accepted into the household cookbook" as a durable fact, only re-run a query. Grocy has no comparable concept. `PLAN.md`'s "Automatic Cookbook Growth" flow needs a genuine membership relationship; neither system provides one to copy. | `implement-recipe-discovery` |
| **Database schema discipline** (foreign keys, automated tests) | **OMIT Grocy's practice explicitly** | Grocy — years of real production use — has zero declared foreign keys anywhere (`PRAGMA foreign_keys=0` on every table checked) and no automated test suite at all. It works despite this, but the same investigation independently reproduced a live data-integrity bug of exactly the kind FK constraints and tests exist to catch early. Cited as concrete motivation for this project's CI-enforced layering and FK-everywhere discipline, not a pattern to weigh against convenience. | `establish-enforced-go-architecture` |

## Cross-check against `PLAN.md`'s Phase 3 domain-model candidates

Per `establish-reference-lab` task 6.4 — for each `PLAN.md` Phase 3 candidate, whether this
research supports, contradicts, or leaves it open:

| PLAN.md candidate | Research verdict |
|---|---|
| Household / Account / Person / HouseholdMembership split | **Supports strongly.** Mealie's user/person conflation is a confirmed, concrete limitation this split avoids. |
| Preferences vs. Restrictions (never scored as one) | **Left open by both systems** — neither Mealie nor Grocy models a hard-restriction/allergy concept distinct from ordinary preference data; no reference evidence either way. Decision stands entirely on `PLAN.md`'s own safety reasoning. |
| RecipeFamily / Variant / Revision | **Supports strongly.** Confirmed real gap (zero revision history in Mealie) plus a live-reproduced corruption bug from mutate-in-place editing. |
| Meals (planned vs. actual) | **Supports.** Mealie's meal-plan-to-recipe link and Spisordning's existing `meal_event`/`meal_plan` split both already separate these; no contradiction found. |
| Favorites (person-scoped, not global) | **Supports strongly.** Mealie's rating-retrofit incident is direct evidence for scoping from day one. |
| Ratings (per-person, per-meal-instance) | **Supports strongly.** Same evidence as Favorites. |
| Ingredient vs. Product | **Supports, informed by both systems' partial models** — neither Mealie's Food nor Grocy's Product alone matches the split; the two-tier model is validated as necessary precisely because neither reference system unifies it. |
| Ingredient Forms (fresh/dried/canned/frozen) | **Left open** — neither system was found to model ingredient form as a first-class, queryable concept (Mealie's Food is form-agnostic; Grocy's Product-per-form requires a distinct Product per form rather than a Form attribute). No reference evidence to validate or contradict the `IngredientForm` design; stands on `PLAN.md` reasoning. |
| Ingredient Substitution (directional, categorized, ratio) | **Left open** — no substitution modeling found in either system. |
| Unit System (universal dimensions distinct from ingredient-specific conversion) | **Supports the *distinction*, contradicts nothing, validates caution.** Grocy's conversion bug is direct evidence that this is genuinely hard to get right, reinforcing why the universal-vs-ingredient-specific split (never a global density) matters — not evidence against the approach, evidence for building it carefully. |
| Retailer Identity (Ingredient ← Product ← RetailerProduct → StoreOffer) | **Out of scope for this research pass** — neither Mealie nor Grocy models retailer-specific SKUs or store-level pricing; this candidate is validated only by its absence from both (nothing to contradict it), tracked in Epic F. |
| Pantry (lot-based, not `products.current_quantity`) | **Supports strongly.** Grocy's own `stock` table is provably insufficient alone (deletes rows at zero) — the exact anti-pattern `PLAN.md` names. |
| Inventory Uncertainty (EXACT/LIKELY/ESTIMATED/UNKNOWN) | **Left open, explicitly.** See matrix row above — Grocy has no uncertainty concept at all. |
| Inventory Events (the seven-verb list) | **Refines, not contradicts.** Six real event kinds, not seven — `MARK_EMPTY` is UI sugar in the only system that has years of production experience with this exact domain. |

## Methodology note

Both investigations combined live-instance interaction (representative test data actually
created and exercised through purchase/consume/discard/transfer/adjust workflows for Grocy;
recipe import, editing, meal planning, ratings for Mealie), direct SQLite inspection of each
system's database after each action (`pct exec` into their Tengil-deployed reference-lab
containers), and reading each project's actual GitHub source and migration history — not
documentation alone. Where a finding is described as "confirmed" or "reproduced," it was
observed directly in this session, not inferred from documentation.
